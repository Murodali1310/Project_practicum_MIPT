## Оптимизация и Индексы

### 1. Оптимизация

#### 1.1. Жизненный цикл запроса, план запроса.

**Что происходит после того, как мы написали запрос?**

1. Создается **подключение к СУБД**. В СУБД отправляется запрос в виде обычного текста.
2. Парсер **проверяет корректность синтаксиса** запроса и создает **дерево запроса**.
3. Система переписывания запросов (rewriting) преобразует запрос – в итоге получаем обновленное дерево запроса; используется [система правил](https://www.postgresql.org/docs/8/rules.html).
4. Планировщик / оптимизатор создает **план запроса**.
5. Обработчик рекурсивно обходит план запроса и возвращает результирующий набор строк.

**Дерево запроса** — это внутреннее представление запроса, включающее:  
- Тип команды (`SELECT, UPDATE, DELETE, INSERT`)  
- Список используемых отношений (таблиц, представлений и т.д.)  
- Целевое отношение для вставки или обновления  
- Список полей (оператор `*` разворачивается в полный список)  
- Список ограничений (`WHERE` и т.д.)

#### 1.1.2. План запроса. Чтение плана, EXPLAIN и ANALYZE.

**Планировщик (planner)** – компонент PostgreSQL, выбирающий наиболее эффективный способ выполнения запроса.

Оператор [EXPLAIN](https://postgrespro.com/docs/postgresql/9.6/sql-explain) показывает план выполнения запроса, который сгенерирует планировщик, не выполняя сам запрос.  
Оператор `EXPLAIN (ANALYZE)` выполняет запрос и показывает фактические затраты.

Пример:
```sql
EXPLAIN SELECT * FROM my_table;
```
Результат может показать:
```  
QUERY PLAN
Seq Scan on my_table (cost=0.00..18334.00 rows=1000000 width=37)
```

- `Seq Scan` означает последовательное сканирование таблицы.
- `cost` – оценочные затраты.
- `rows` – предполагаемое количество возвращаемых строк.
- `width` – средний размер строки в байтах.

Чтобы обновить статистику, используем команду `ANALYZE`:
```sql
ANALYZE my_table;
```

После `ANALYZE`, если выполнить:
```sql
EXPLAIN (ANALYZE) SELECT * FROM my_table;
```
получим фактическое время выполнения, реальное количество строк, а также время планирования и общее время исполнения.

### 1.2. Индексы

**Индекс** — структура данных, ускоряющая поиск строк в таблице. Он хранится отдельно от данных таблицы. Индексы могут быть использованы для:
- Ускорения выборок, особенно при селективных условиях (`WHERE`).
- Поддержки некоторых ограничений целостности (например, UNIQUE).

**Важные моменты об индексах:**
- Любой индекс можно удалить и перестроить заново.
- Изменения данных, влияющие на индексируемые поля, могут замедлять запросы из-за необходимости поддерживать индекс в актуальном состоянии.
- Индексы работают тем лучше, чем более узок результат запроса (высокая селективность).
- Есть несколько стратегий сканирования данных через индексы, в частности `Index Scan`, `Bitmap Index Scan`, `Index Only Scan`.

**Синтаксис:**
```sql
CREATE INDEX ON my_table(column_2);
DROP INDEX index_name;
```

### 1.3. Способы считывания данных

#### 1.3.1. Seq Scan (Последовательный скан)
Чтение таблицы целиком. Эффективно при больших объемах выборки или отсутствии подходящего индекса.

#### 1.3.2. Index Scan (Индексное сканирование)
Чтение данных через индекс по условию `WHERE` с высокой селективностью. Ускоряет поиск, но не всегда выгодно при возвращении большого числа строк.

#### 1.3.3. Bitmap Index Scan
Сначала строится битовая карта страниц, в которых могут находиться искомые строки, а затем выбираются данные. Выгодно при средних объемах выборки.

#### 1.3.4. Index Only Scan
Если все нужные данные уже есть в индексе (покрывающий индекс), можно не обращаться к таблице, что существенно ускоряет запрос.

#### 2.2. Курсоры

**Курсор** – объект, позволяющий пошагово получать результат запроса.  
Позволяет работать с большими наборами данных, не загружая их все сразу в память.

В PL/pgSQL:
```sql
DECLARE
    curs1 refcursor;
    curs2 CURSOR FOR SELECT * FROM tenk1;
    curs3 CURSOR (key integer) FOR SELECT * FROM tenk1 WHERE unique1 = key;
```

## Практические задачи (Индексы)


1.
   - Создайте таблицу `items(id SERIAL PRIMARY KEY, name TEXT, category_id INT, price NUMERIC)`.
   - Заполните таблицу `items` случайными данными (например, 100000 строк).
   - Выполните запрос:
     ```sql
     EXPLAIN (ANALYZE) SELECT * FROM items WHERE name = 'SomeName';
     ```
     Обратите внимание на используемый метод чтения данных и затраты.
   - Создайте индекс по полю `name`:
     ```sql
     CREATE INDEX idx_items_name ON items(name);
     ```
   - Повторите запрос и сравните план: стало ли быстрее, использовался ли теперь индекс?

2. **Выборка с разными условиями:**
   - Выполните:
     ```sql
     EXPLAIN (ANALYZE) SELECT * FROM items WHERE price > 500;
     ```
     Посмотрите, какой метод сканирования выбран.
   - Создайте индекс по полю `price`:
     ```sql
     CREATE INDEX idx_items_price ON items(price);
     ```
   - Повторите запрос и сравните результаты.  
     Изменилось ли время выполнения? Какой метод сканирования теперь используется?

3. **Сложный запрос и Bitmap Index Scan:**
   - Попробуйте выполнить запрос:
     ```sql
     EXPLAIN (ANALYZE) SELECT * FROM items
     WHERE category_id = 10 AND price < 100;
     ```
   - Создайте два индекса:
     ```sql
     CREATE INDEX idx_items_category_id ON items(category_id);
     CREATE INDEX idx_items_price ON items(price);
     ```
   - Повторно выполните запрос, обратите внимание, не использует ли теперь PostgreSQL Bitmap Index Scan с объединением битовых карт?

4. **Index Only Scan:**
   - Добавьте в запрос только те поля, которые входят в индекс:
     ```sql
     CREATE INDEX idx_items_name_price ON items(name, price);
     ```
   - Выполните:
     ```sql
     EXPLAIN (ANALYZE) SELECT name, price FROM items WHERE name = 'SomeName';
     ```
   - Проверьте, будет ли применен Index Only Scan (особенно, если поле `name` и `price` полностью покрывают запрос).
